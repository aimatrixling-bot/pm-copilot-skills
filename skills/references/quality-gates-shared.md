# PM Copilot 共享质量机制

> 本文件被 Agent CLAUDE.md 和各 Skill 引用，定义跨所有 Skill 共享的质量增强机制。

---

## 零、保真度分级协议

本文件定义的检查机制按保真度分级执行：

| 段落 | Draft | Review（默认） | Release |
| --- | --- | --- | --- |
| 一、一致性检查 | 仅 User Journey ⊆ In Scope | 全部 4 条 | 全部 4 条 |
| 二、可行性挑战 | 不触发 | 命中触发词时触发 | 命中触发词时触发 |
| 三、风险缓解格式 | 不强制 4 字段 | 强制 4 字段 | 强制 4 字段 + 要求 ≥1 个边缘场景 |
| 四、反合理化 | 不检查 | 全部 | 全部 |
| 五、Loophole Detection | 不触发 | 不触发 | 强制执行 |
| 六、反向提问 | 1 个 | 2 个 | 3 个 |

用户显式声明 `fidelity` 标签时按标签执行；未声明时默认 Review。推断规则见 Agent CLAUDE.md Iron Law 约束段落。

## 零点五、对话输出格式协议（所有保真度均执行）

Skill 在**对话中**直接呈现给用户的文本产出必须遵守以下规则：

- [ ] **格式匹配产出类型** — 文档类（PRD/竞品分析/决策记录等）用纯 Markdown；原型/代码类按技术栈输出（HTML/React/TS）；文件导出类（docx/pdf/pptx）由对应 Skill 按目标格式处理
- [ ] **对话文本禁止非渲染标签** — 对话中的文本产出不得包含 `<generative-ui-widget>`、`<style>`、`<script>` 等无法在 Markdown 渲染中正确显示的标签
- [ ] **文档类产出不包裹代码围栏** — PRD 等文档内容直接输出为 Markdown，不放在 ```` ```markdown ``` ```` 中（代码片段本身除外）
- [ ] **Agent 说明与正文分离** — Agent 的解释性说明（意图解读、执行路径、自检备注）放在产出物之前或之后，与 Skill 模板产出物明确分隔

## 零点六、默认语言协议（所有保真度均执行）

PM Copilot 的用户可见输出默认使用**中文为主**。英文只在以下情况保留：

- 代码、API、文件路径、命令、配置项、包名、字段名、枚举值、测试名、commit message 等工程标识。
- 行业通用术语或本项目约定术语，如 `Intent Packet`、`Output Packet`、`Evidence Packet`、`Sensor Gates`、`Go/No-Go`、`MVP`、`PRD`。
- 需要与运行时、平台、插件、技能触发描述保持兼容的英文名称。

### 输出规则

- 面向用户的解释、报告、验收结论、风险、建议、检查清单，应使用中文表达。
- 首次出现的关键英文术语建议写成"中文名（English Term）"，例如"证据包（Evidence Packet）"。
- 不要把整份验收文档、README、benchmark、原型 UI 文案写成英文，除非用户明确要求英文。
- 状态码可保留英文，但应在上下文中给出中文含义，例如 `PASS（通过）`、`PARTIAL（部分通过）`、`BLOCKED（阻塞）`、`NO-GO（不建议发布）`。
- 代码中的用户可见错误信息、推荐理由、阻塞原因、按钮文案，也默认中文。

## 一、一致性检查协议

当交付物包含多个部分（如 Problem Statement + User Journey + Scope + Metrics + Risks）时，交付前必须验证：

- [ ] **User Journey ⊆ In Scope** — 用户旅程/使用流程中每个步骤都在 In Scope 中有对应功能，Out of Scope 功能不出现在 MVP 旅程中
- [ ] **功能引用自洽** — 所有功能引用 ⊆ 当前文档定义的功能集（不引用未定义的功能）
- [ ] **指标可追溯** — 所有成功指标引用都有对应的基线 + 目标 + 测量方式
- [ ] **风险缓解可执行** — 每个风险项有具体缓解措施（不是"持续监控"、"关注"等）

违反任一条 = 立即修正后才能交付。

## 二、可行性挑战触发词表

当输出中包含以下模式词时，**必须触发【技术实现猜想】**：

| 触发词 | 风险级别 | 要求的动作 |
| --- | --- | --- |
| 跨平台 / 多平台聚合 / 多平台同步 | 高 | 必须命名具体的 API / 协议 / 数据源，不是抽象的"集成" |
| 批量发送 / 批量操作 | 高 | 必须解释批处理机制、限流策略、失败重试 |
| 自动追踪 / 自动同步 / 自动更新 | 高 | 必须指定数据源和轮询/webhook 机制 |
| 实时 / 即时 | 中 | 必须定义延迟预算和可接受范围（如 P95 < 3s） |
| 一键部署 / 一键发送 / 一键XX | 中 | 必须列出隐藏的前提条件 |
| AI 自动 / 智能 XX | 中 | 必须定义模型输入/输出和降级方案 |
| 无缝集成 | 中 | 必须命名集成点（API 端点、webhook URL、SDK 方法名） |
| 全平台 / 所有 XX | 低 | 必须明确列举包含和不包含哪些平台/项目 |
| 第三方 / 外部系统 | 低 | 必须指定集成类型（官方 API / 爬虫 / RPA / 邮件 / 手动） |

### 【技术实现猜想】格式

对每个命中的触发词，在输出中以标注块形式补充：

```
**[触发]** _命中的触发词_
**[路径]** 具体技术路径（不是"使用 API"而是"调用供应商 REST API v2 /orders/batch 端点，限流 100/min"）
**[失败回退]** 如果此路径不可行，最简替代方案是什么？
**[最小可行方案]** 去掉此功能的今天就能发布的版本是什么？
```

如果用户说"不需要可行性分析"，可以跳过但必须标注 `[skip-feasibility-check: 用户确认]`。

## 三、风险缓解强制格式

每个风险项**必须**包含以下 4 个字段：

| 字段 | 要求 | 差的示例 | 好的示例 |
| --- | --- | --- | --- |
| **风险** | 具体场景，不是类别 | "性能风险" | "搜索响应时间 > 2s，当商品目录超过 1 万件时" |
| **缓解** | 具体动作，不是"监控" | "持续监控系统" | "预计算 Top 100 查询的搜索索引；长尾查询显示加载动画" |
| **指标** | 可衡量的护栏 | — | "P95 搜索延迟 < 1.5s；如果 P95 > 3s → 显示降级结果横幅" |
| **负责人** | 谁来执行 | "团队" | "后端工程师 + SRE 发布周值班" |

缓解方案写"持续监控"或"关注"等同于没有缓解。必须替换为具体动作。

## 四、反合理化补充表

以下借口在可行性检查时特别容易出现，必须警惕：

| 你可能在想的 | 真相 |
| --- | --- |
| "这个集成很标准" | "标准集成"通常忽略了认证、限流、错误处理、版本兼容 |
| "技术细节可以之后再补" | 没有《技术实现猜想》的需求是愿望，不是需求 |
| "这个风险已经在风险区了" | 列出风险 ≠ 缓解风险。没有具体缓解的风险项是占位符，不是保障 |
| "用户旅程是高层的，不需要和 Scope 匹配" | 每个用户旅程步骤都隐含对功能的承诺。Out of Scope 的步骤 = 未承诺的承诺 |
| "AI 会处理边缘情况" | "AI"不是技术方案。哪个模型？什么输入？什么降级？什么准确率阈值？ |
| "这个场景不太可能发生" | "不太可能" ≠ "不会发生"。未定义的行为 = 未定义的用户体验 |

## 五、Loophole Detection（仅 Release 保真度触发）

当保真度为 Release 时，在一致性检查之后额外执行漏洞检测。

### 触发条件

交付物中包含以下任一元素时触发：

- 状态流转（实体有 ≥ 2 种状态）
- 多角色协作（≥ 2 种角色参与同一流程）
- 时间依赖（流程中有先后顺序的时间节点）
- 资源所有权转移（数据/客户/任务在不同角色间流转）

### 检测方法

对每个触发的元素，逐一检查：

1. **状态转换完整性** — 每个状态是否有明确的前置状态和后续状态？是否存在"只能进不能出"的状态？
2. **角色交接定义** — 资源/任务从角色 A 转到角色 B 时，交接条件是否明确？交接失败如何处理？
3. **时间窗口边界** — 有时间限制的流程，超时后如何处理？提前完成是否有影响？
4. **并发冲突** — 两个角色同时操作同一资源时，冲突如何解决？
5. **回退路径** — 流程走到某步需要回退时，是否定义了回退规则？

### 输出格式

检测到漏洞时，在交付物中追加：

```markdown
## 漏洞检测结果

| # | 场景 | 未定义的行为 | 建议补充规则 | 优先级 |
| --- | --- | --- | --- | --- |
| 1 | {场景描述} | {当前文档未覆盖的行为} | {建议的最小规则定义} | P0/P1 |
```

检测到 0 个漏洞时，输出：`**漏洞检测**: 未检测到逻辑漏洞（基于当前文档定义范围）。`

## 六、反向提问机制（所有保真度均适用）

交付物末尾的"下一步"段落中，自动追加反向提问，引导用户思考。

### 格式

```markdown
## 反向提问

> 交付物已完成。在继续之前，考虑以下问题：

1. **{关键假设验证}**: 如果 [{核心假设}] 不成立，这份文档中最先需要改的是哪个部分？
2. **{下一步优先级}**: 下一步建议执行 {Skill 名}，但你是否更需要先 [{替代动作}]？
3. **{未覆盖的视角}**: 这份文档是否需要 [{不同受众}] 的视角补充？
```

### 选择规则

- 提问 1：来自交付物中置信度最低的假设
- 提问 2：推荐当前阶段的下一个 Skill，但提供替代选项
- 提问 3：基于交付物受众的盲点（如 PRD 是否考虑了技术视角、竞品分析是否考虑了用户视角）

提问数量：Draft 1 个，Review 2 个，Release 3 个。

## 七、用户不满时的诊断引导

当用户对产出表达不满时（触发信号："不对"、"不是这个意思"、"重来"、"没用"、"搞错了"），不要直接重试。先引导用户定位根因。

### 流程

1. 识别不满信号
2. 判断属于哪类根因（参考 `references/pm-debug-guide.md`）：
   - Context 缺失（AI 拿不到判断所需的输入）
   - Context 饱和（关键信息被稀释）
   - 指令歧义（请求有多种合理理解）
   - 能力边界（任务超出当前稳定能力）
3. 针对性修复（补信息 / 精简输入 / 改写目标 / 换策略）

### 与反向提问的关系

- 反向提问在**交付后**触发，预防下一个决策失误
- 诊断引导在**不满时**触发，修复当前产出问题
- 两者互补，不冲突

## 八、Intent Packet 模板（共享）

所有非 reference 类 skill 的 `## Intent Packet` 章节应捕获以下最小字段集。详细格式见 `skills/skill-template.md`。

**最小字段集**：

| 字段 | 必填 | 说明 |
|---|---|---|
| **Want** | 是 | 剥离解决方案后的问题本质（一句话） |
| **Constraints** | 是 | 硬性限制，来自用户明示或项目 CLAUDE.md 推断 |
| **Context Sources** | 是 | 上下文文件路径（Glob + Read 确认存在） |
| **Depth** | 否 | Draft / Review / Release，未声明默认 Review |
| **Output Target** | 否 | 产出受众和场景 |

**未提供时的处理**：标注 `[假设]`，交付前确认。不得因信息缺失跳过 Intent Packet 捕获。

**与上游 Output Packet 的关系**：当 skill 作为 pipeline 下游时，Context Sources 字段应引用上游 skill 的 Output Packet。

## 九、Gate 格式规范（共享）

有分支决策的 skill 使用 `## Gates` 章节声明检查点。Gate 不是 Iron Law 的重复——Iron Law 是不可跳过的铁律，Gate 是流程中的决策点。

**Gate 表格列定义**：

| 列 | 说明 |
|---|---|
| **Gate** | 命名标识（G1/G2/G3 + 简述） |
| **位置** | 在执行流程的哪一步之后 |
| **通过条件** | 明确的、可验证的条件（不是"质量好"） |
| **失败处理** | Pause（暂停修正）/ Risk（标注风险继续）/ Nudge（提示用户决策） |

**失败处理三态**：
- **Pause**：产出有错误，必须修正后才能继续
- **Risk**：产出方向正确但有风险，标注 `[风险]` 后继续，交付前复查
- **Nudge**：产出合格但存在更优路径，提示用户选择

**重试上限**：每个 Gate 最多重试 2 次，第 3 次失败向用户报告而非继续循环。

## 十、Meta-Review 标准问题集（共享）

所有 skill 的 `## Meta-Review` 章节，在交付完成后执行 post-delivery 自审。这与 `## 交付前检查`（pre-delivery）互补。

**3 个标准自审问题**（所有 skill 必问）：

1. **方法论骨架**：产出是否遵循了本 skill 声明的方法论？（对照执行流程的每个 Step）
2. **反理实化警惕**：表格中的"你可能在想的"是否真的被警惕了？（逐条对照）
3. **Iron Law 验证**：每条铁律是否已验证满足？（非"应该满足"而是"已验证满足"）

**扩展问题**（各 skill 可定制）：

| Skill 类型 | 扩展问题示例 |
|---|---|
| pipeline skill | Output Packet 的 key_decisions 是否可追溯到 Iron Law？ |
| 分析类 skill（comp/deconstruct） | 结论是否有数据/来源支撑，非仅推断？ |
| 代码类 skill | 变更是否精确（只改必须改的）？ |

**自审结果格式**：1-2 句话附在交付物末尾。例如：`Meta-Review: 方法论骨架已遵循，Iron Law 3 条已验证，反理实化 #2 触发并已处理。`

**不通过时**：回到对应步骤修正，不在 Meta-Review 阶段打补丁。

## 十一、Evolution Writeback 协议（共享）

所有 skill 的 `## Evolution Writeback` 章节，在执行后捕获可回写的观察。

**观察捕获三问**：

1. **方法论偏差**：skill 的方法论骨架是否有不够贴合实际的地方？
2. **反理实化补充**：是否遇到了表格未覆盖的新借口模式？
3. **边界调整信号**：Capability Index 的 CAN/CANNOT 是否需要调整？

**记录决策树**：

```
有观察？
├─ 是 → 置信度评估
│   ├─ 高（跨项目可复用）→ 建议回写到 skill-template.md 或 quality-gates-shared.md
│   ├─ 中（特定场景有效）→ 记录到 docs/evolution-log.md
│   └─ 低（偶发现象）→ 仅对话中提示用户，不记录
└─ 否 → 跳过此章节，不强写
```

**记录文件**：`docs/evolution-log.md`（项目级，不存在时由首次记录创建）

**记录格式**：

```markdown
## YYYY-MM-DD — [Skill Name] — [项目/场景]
- **观察**: [一句话描述]
- **建议回写**: [回写到哪个文件/章节 / "仅记录不回写"]
- **置信度**: 高/中/低
```

**约束**：不自动回写——只捕获和建议。回写决策由用户确认。

## 十二、Capability Index 声明规范（共享）

所有 skill 的 `## Capability Index` 章节，显式声明能力边界和转交规则。

**三列定义**：

| 列 | 说明 |
|---|---|
| **维度** | 任务类型 / 输出格式 / 深度范围（至少覆盖这 3 个维度） |
| **CAN** | 该 skill 可以做的事（2-4 项核心能力，具体而非泛化） |
| **CANNOT → HANDOFF** | 不做的事 + 转交目标 skill（格式：`[不做的事] → [目标 skill]`） |

**HANDOFF 规则**：
- 必须命名具体的转交目标 skill（不是"其他 skill"）
- 如果没有合适的 skill 可转交，标注 `[无对应 skill，建议人工处理]`
- HANDOFF 时附 1 句话说明为什么该 skill 更合适

**示例**（pm-discovery）：

```markdown
| **任务类型** | 问题定义、用户画像、竞品分析、Go/No-Go 决策 | 写 PRD → pm-prd | 写代码 → pm-code-implement |
| **深度范围** | 从想法到验证报告 | 已有 PRD 需要迭代 → pm-prd |
```

**边界原则**：宁可显式拒绝并指向更合适的 skill，不在能力边界外硬撑。CANNOT 行的存在不是缺陷，是诚实。

## 十三、Evidence Packet 协议（Builder OS）

代码、发布、审查、原型验证、Agent 工作流等 Builder 类任务，完成声明必须附证据。目标是避免"应该可以"、"之前跑过"、"看起来没问题"。

### 触发条件

任一条件命中时，交付物必须包含 Evidence Packet：

- 改动了代码、配置、脚本、构建产物
- 声称完成了实现、修复、审查、发布准备
- 声称通过了测试、构建、类型检查、视觉验证
- 需要交给下游 skill、工程师、发布负责人继续执行

### 最小字段

| 字段 | 要求 | 不合格示例 |
|---|---|---|
| **Artifacts** | 文件路径、报告路径、截图路径或产物路径 | "已生成" |
| **Checks Run** | 命令 + 关键输出；未运行必须说明原因 | "测试通过" |
| **Manual Verification** | 需要人工确认的路径、截图、步骤 | "看起来正常" |
| **Open Risks** | 未验证项、降级项、需要人工审查点 | "无风险"但未解释 |
| **Completion Claim** | PASS / PARTIAL / BLOCKED + 理由 | "done" |

### Completion Claim 规则

- **PASS**：所有必须证据存在，且未留阻塞风险。
- **PARTIAL**：主要产出完成，但存在未运行检查、人工待验或非阻塞风险。
- **BLOCKED**：缺关键输入、关键检查失败、或风险不可接受。

没有当场证据，不得写 PASS。

## 十四、Sensor Gates 协议（Builder OS）

Sensor Gate 处理确定性检查：能用脚本、测试、清单、构建、截图或审查证明的，不依赖模型自觉。

| Sensor | 触发场景 | 检查方式 | 失败处理 |
|---|---|---|---|
| **Spec Coverage** | PRD / 原型 / 代码交付 | 对照需求条目、Feature Frame、Design Brief | Pause -> 补齐缺口或标注未覆盖 |
| **Design-before-Code** | UI / 前端实现 | 先确认 Feature Frame / PRD / Design Brief / 截图 | Pause -> 先补设计输入 |
| **Fake UI Detection** | 原型或前端 UI | 按钮、提示、状态、空页面是否对应真实行为 | Pause -> 实现真实行为或删除假引导 |
| **Fake Test Detection** | 声称测试通过 | 断言是否证明真实行为；是否只测 happy path | Pause -> 重写测试或降级声明 |
| **Build/Test Evidence** | 代码变更 | typecheck / lint / unit / build / smoke | Pause -> 修复根因；同问题 3 次失败停手重审 |
| **Release Artifact** | 发布/打包 | 从安装包或发布产物验证，而非仅 dev 环境 | Block -> 重新构建和验证 |
| **Privacy/Security Audit** | 发布、集成、权限、日志 | secrets、PII、开发者路径、权限、敏感日志 | Block -> 修复后重新扫描 |
| **Overengineering Check** | 架构/实现/重构 | 是否新增不必要抽象、依赖、API、死代码 | Pause -> 简化到满足目标的最小结构 |

### 使用原则

- Draft 保真度可只记录建议执行的 Sensor。
- Review 保真度执行与当前产出直接相关的 Sensor。
- Release 保真度必须执行所有命中的 Sensor，并在 Evidence Packet 中记录证据。
- Sensor Gate 失败不能用文字解释绕过；只能修复、降级声明、或请求人工决策。

## 十五、Goal Suitability 协议（Builder OS）

Goal-driven execution 只适合标准清晰、证据可验、风险可控的任务。它不能替代产品判断。

### 适合交给 Goal 的任务

- 执行已确认的开发计划某个 phase
- 按既定架构实现一个边界明确的子任务
- 修复有复现步骤和验证命令的 bug
- 生成可用清单验证的发布准备材料
- 执行批量、重复、可回滚的资料整理

### 不适合交给 Goal 的任务

- 需求访谈、用户判断、市场定位还不清楚
- 成功标准只能靠主观满意度判断
- 涉及生产权限、资金、隐私、删除、不可逆迁移且无人工审批
- 多方决策未定，任务范围会在执行中持续变化

### Goal Packet 最小字段

```markdown
## Goal Packet

- **objective**: [一句话目标]
- **scope**: [包含范围]
- **non_goals**: [明确不做]
- **constraints**: [文件/权限/时间/风险边界]
- **verifiable_completion_criteria**: [逐条可证明的完成条件]
- **checks_to_run**: [命令/清单/人工验证]
- **expected_evidence**: [需要贴出的输出/文件/截图/报告]
- **stop_conditions**: [何时停止并请求用户]
```

## 十六、Eval Notes 协议（Skill 变更）

Skill、模板、共享门禁、触发描述、handoff 规则、Capability Index 的变更，都应留下评测意图。复杂变更再进入正式 eval 工作区；小变更至少写明人工评审点。

### 触发条件

- 新增 skill / 删除 skill / 合并 skill
- 改 `description`、`argument-hint` 或触发词
- 改输出契约、Output Packet、Evidence Packet
- 改安全、隐私、发布、代码执行边界
- 改共享模板或质量门禁

### 最小记录

```markdown
## Eval Notes

- **Change type**: [new skill / behavior change / trigger change / reference update]
- **Should-trigger examples**: [2-3 个真实用户请求]
- **Should-not-trigger examples**: [2-3 个相邻但不应触发的请求]
- **Quality checks**: [人工评审点或脚本断言]
- **Regression risk**: [可能影响的 skill / workflow]
```

**规则**：影响触发或安全边界的变更，不能只写"文档更新"。必须给出 should-trigger / should-not-trigger 样例。

## 十七、反膨胀准入规则（Builder OS）

新增 skill / agent / command / hook 前，必须通过以下准入测试。

| 准入问题 | 通过标准 |
|---|---|
| **独立触发条件** | 用户请求有清晰信号，且不会与现有 skill 高度重叠 |
| **独立输出契约** | 产出结构、证据要求或 handoff 与现有 skill 不同 |
| **复用频率** | 至少 3 个真实或高可信复用场景 |
| **不可替代性** | 不能用现有 skill + reference + checklist 低成本覆盖 |
| **平台适配性** | 不依赖单一 runtime 的私有能力，或已声明 adapter 限制 |
| **验证路径** | 有 eval、脚本、清单或人工评审方式证明它更好 |

未通过时，优先选择：

1. 写入 `skills/references/` 作为 reference
2. 加入现有 skill 的 Capability Index / Sensor Gate
3. 作为 optional pack 记录，暂不进入 core
4. 只作为项目级规则，不污染通用包
