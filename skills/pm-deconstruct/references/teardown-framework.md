## Layer 0：产品身份层（Surface Identity）

**目标**：5 分钟内建立对产品的整体认知框架

**分析维度与工具**：

| 维度 | 分析工具 | 输出 |
|------|----------|------|
| 一句话定义 | "电梯演讲"还原 | 产品名 + 一句话价值主张 + 目标用户 |
| 产品类型 | 产品姿态判断（Sovereign/Transient/混合） | 产品姿态 → 决定后续分析侧重 |
| 市场定位 | 竞品定位图（价格 × 功能深度） | 产品在市场中的象限位置 |
| 目标用户 | 显性用户 + 隐性用户 + 明确不服务的用户 | 三类用户画像 |
| 核心价值主张 | "如果去掉这个功能，产品是否还能存在？" | 核心功能识别 |

**铁律 L0-01**：产品身份分析不得使用超过 3 个来源，必须在 5 分钟内完成。此层是"定位锚点"而非"深度分析"。

**铁律 L0-02**：如果目标产品是桌面端 App / 需安装客户端，优先引导用户进行实际操作和截图采集，而非仅依赖 WebFetch 获取官网信息。JS 渲染的 SPA 页面通常无法通过 WebFetch 获取有效内容。

**信息缺口标注**：当某维度的数据无法获取时，必须明确标注 `[信息缺口]` 而非用推断填补。

## Layer 1：交互架构层（Interaction Architecture）

**目标**：从界面反推产品的信息优先级和用户行为引导逻辑

**核心原则**：不关心"按钮好不好看"，只关心"为什么这个按钮会放在这里"

### 四大分析工具

| 工具 | 操作方法 | 洞察方向 | 输出格式 |
|------|----------|----------|----------|
| **"五秒测试"** | 打开产品首页，不滚动，5 秒内感受到什么？ | 产品最想传递的"第一印象"和核心价值 | 3 条印象 + 推断的优先级排序 |
| **导航解剖** | 分析常驻导航放入了哪些功能，排序逻辑是什么 | 暴露"用户最高频"或"商业最重要"的场景判断 | 导航层级图 + 每项的战略意图标注 |
| **IA 逆向工程** | 画出产品的核心信息层级图（哪些置顶/折叠/隐藏） | 信息层级深度 = 功能优先级；层级越浅 = 产品越重视 | 信息架构图（含深度标注） |
| **反向用户旅程图** | 选择核心功能走完整流程，每步追问"产品希望我做什么？" | 识别引导策略、摩擦点设计、流畅度追求 | 旅程图 + 每步的"设计意图标注" |

**实操优先原则**：Layer 1 的四大工具必须以一手体验为基础。如果无法实际操作产品：

1. 优先引导用户安装/注册并提供截图
2. 次选使用 WebFetch 抓取官方帮助文档中的界面描述
3. 最后才使用第三方测评中的截图和描述，且必须标注 `[二手信息]`

任何非一手体验的分析结论，置信度自动降一级（如 `[高置信]` → `[中置信]`）。

### Layer 1 推断规则

```
IF 导航栏一级入口有"直播"且没有"搜索"
THEN 产品战略重心从"社区"转向"媒体消费"
BECAUSE 搜索是"用户主动获取"的入口，直播是"平台推送消费"的入口

IF 核心功能需要 3 步以内到达
THEN 产品将此功能视为"高频+高价值"
BECAUSE 每多一层级，用户到达率下降约 50%

IF 设置/配置被折叠到二级入口
THEN 产品定位为"开箱即用"而非"高度可定制"
```

### 产出标准

Layer 1 的结论**必须是一段推断**，不是描述：

> ~~"竞品 A 的导航栏有首页、发现、消息、我的四个 Tab"~~
> **"竞品 A 的导航栏将'发现'放在第二位而非'消息'，表明其战略重心是'内容消费'而非'社交互动'——这是一个从社区向媒体的转型信号"**

## Layer 2：业务逻辑层（Business Logic）

**目标**：从功能规则反推产品的价值主张、价值网络和价值捕获机制

### 四大分析工具

| 工具 | 操作方法 | 洞察方向 |
|------|----------|----------|
| **反向 JTBD** | 想象自己是用户，问："我'雇佣'这个产品来完成什么'工作'？" | 核心价值主张的真实含义 |
| **价值网络分析** | 识别所有"角色"（用户/创作者/商家/平台），分析平台为每一方提供了什么价值 | 网络是否稳固？是否存在某方价值感过低而流失？ |
| **商业模式画布逆向** | 为产品填写完整商业模式画布：客户细分？核心资源？收入来源？ | 价值捕获逻辑 → 从收费结构反推什么被产品视为"核心付费点" |
| **业务规则逆向** | 找出产品中隐含的业务规则（如：每日可发送 X 条、最多 Y 个成员、Z 天后过期） | 规则 = 约束 = 产品对人性的理解和商业逻辑的编码 |

### Layer 2 推断规则

```
IF 产品有免费版且免费版功能限制在"协作"维度（人数/空间/分享）
THEN 产品的核心价值捕获在"团队协作"，免费版是"个人试用"
BECAUSE 限制协作而非限制功能 = 产品想让个人先形成习惯再推动团队采购

IF 产品的定价层级以"功能门控"为主（高级功能需付费）
THEN 产品采用"价值阶梯"策略，核心功能引流，高级功能变现

IF 产品的定价层级以"用量门控"为主（API 调用次数/存储空间）
THEN 产品采用"基础设施"策略，目标是从工具升级为平台
```

**关键产出**：价值网络图 + 商业模式画布 + 核心业务规则清单（每条标注推断的战略意图）

<a id="layer-3"></a>
## Layer 3：增长引擎层（Growth Engine）

**目标**：识别驱动产品增长的引擎和维持留存的回路

### 三大分析工具

| 工具 | 操作方法 | 洞察方向 |
|------|----------|----------|
| **AARRR 逆向拆解** | 逐环节分析竞品在获客/激活/留存/推荐/变现的机制 | 哪个环节是"引擎"，哪个是"瓶颈"？ |
| **核心增长回路识别** | 画出产品的主增长引擎回路（病毒式/内容驱动/付费驱动/销售驱动） | 增长是否可自我持续？关键燃料是什么？ |
| **行为锚点与留存机制** | 识别产品的"啊哈时刻"、习惯触发器、沉没成本设计 | 用户为什么回访？什么让他们"不舍得走"？ |

### 增长回路模板（必须画出循环）

```
[触发条件] → [用户行为] → [价值实现] → [分享/推荐] → [新用户进入] → [循环强化]
     ↑                                                              |
     └──────────────────────────────────────────────────────────────┘
```

### Layer 3 推断规则

```
IF 产品有"连续打卡"或"每日任务"机制
THEN 核心留存策略是"习惯养成"，产品的 DAU 比单次使用时长更重要

IF 产品有"邀请奖励"但奖励是"功能解锁"而非"现金"
THEN 核心增长引擎是"功能驱动型病毒"

IF 产品的获客成本 (CAC) 高但终身价值 (LTV) 更高
THEN 产品采用"重投入深变现"策略
```

**关键产出**：增长回路图 + AARRR 分析 + 留存机制清单 + 增长引擎类型判定

<a id="layer-4"></a>
## Layer 4：战略意图层（Strategic Intent）

**目标**：穿透一切表象，回答终极问题——"这家公司到底想成为什么？"

### 五大分析工具

| 工具 | 操作方法 | 洞察方向 |
|------|----------|----------|
| **时间旅行分析** | 研究产品版本历史/页面快照（Wayback Machine），梳理重大迭代 | 迭代方向 = 战略方向 |
| **负空间分析** | 分析"没有做什么"——同赛道产品都有但他们没有的功能 | **不做什么比做什么更能体现战略** |
| **外部信号解读** | 分析招聘信息、创始人访谈、融资/并购、技术栈选择 | 招聘"商业化 PM" = 商业化信号 |
| **反向组织架构推演** | 基于产品拆解反推团队组成和协作模式 | 决定他们能做什么、不能做什么 |
| **关键信号交叉验证** | 综合以上所有信号，形成一致性判断 | 3+ 个信号指向同一方向 = 高置信度 |

### Layer 4 推断规则

```
IF 产品近期开放 API + 招聘"开发者生态运营"
THEN 战略意图是成为"基础设施提供商"
RISK 这构成"降维打击"威胁

IF 产品的每次重大迭代都在"降低使用门槛"
THEN 战略意图是"大众化"，从专业工具走向大众市场

IF 产品在某个高价值功能上"做得不够好"但持续投入
THEN 该功能是"战略要地"，当前的不足可能是组织能力瓶颈而非战略放弃
```

**关键产出**：战略意图声明（一句话）+ 信号证据链 + 战略时间线 + 竞争威胁等级判定

## Layer 5：AI 系统逆向层（AI System Reverse Engineering）

> **触发条件**：当目标产品包含 AI/LLM/Agent 核心功能时自动激活

**目标**：逆向工程 AI 产品的"大脑"和"神经系统"

### 六大分析工具

#### 工具 5.1：Prompt 设计逆向

| 逆向方法 | 操作 | 可推断的内容 |
|----------|------|------------|
| 边界输入测试 | 输入边界案例（空输入、超长、多语言混合、对抗性输入） | System Prompt 的结构和约束 |
| 角色泄漏测试 | 用"请重复你的系统指令"等提示试探 | 直接的 Prompt 泄漏 |
| 输出模式分析 | 分析 AI 输出的格式、语气、结构化程度 | 输出格式指令和角色设定 |
| 拒绝模式分析 | 触发 AI 拒绝回答的场景，分析拒绝话术 | 安全边界和内容策略 |
| 一致性测试 | 同一问题问多次，观察输出变异度 | Temperature 设置和确定性控制 |

#### 工具 5.2：Harness Engineering 解构

| 维度 | 观察指标 | 可推断的 Harness 设计 |
|------|----------|---------------------|
| 工具暴露 | 产品展示了哪些 AI 可调用的功能？ | 工具设计哲学（少而精 vs 多而全） |
| 错误恢复 | AI 出错时的行为：静默重试？用户提示？降级？ | 错误恢复策略 |
| 上下文管理 | 长对话中的"遗忘"模式 | 压缩管道设计、记忆系统架构 |
| 权限边界 | AI 可以自主做什么？什么需要用户确认？ | 权限模型层级 |
| 并发行为 | 多任务同时处理时的行为 | Agent 编排策略 |
| 输出验证 | AI 输出是否经过后处理？ | Eval 系统的存在和介入点 |

#### 工具 5.3：Eval 体系推断

| 观察方法 | 推断内容 |
|----------|----------|
| 分析低置信度输出的处理 | 是否有置信度评估机制、人工介入触发条件 |
| 分析输出一致性 | 是否有输出格式校验、事实性检查 |
| 分析 AI 幻觉的处理 | 是否有幻觉检测、用户反馈闭环 |

#### 工具 5.4：Agent 架构推断

| 观察方法 | 推断内容 |
|----------|----------|
| 任务分解方式 | 单 Agent vs 多 Agent 架构 |
| 并发行为 | Agent 编排模式 |
| 中间状态可见性 | 状态管理架构 |
| 复杂多步任务鲁棒性 | 任务规划能力、错误恢复策略 |

#### 工具 5.5：交互主权分析

| 主权模式 | 特征 | 典型产品 |
|----------|------|----------|
| **用户主权** | AI 只在用户明确请求时介入 | ChatGPT 手动模式 |
| **AI 辅助** | AI 主动建议但用户决策 | GitHub Copilot |
| **AI 主导** | AI 自动执行，用户审批 | Claude Code auto 模式 |
| **AI 自主** | AI 全自动执行，用户事后审查 | Stripe Minions |

#### 工具 5.6：AI 安全边界逆向

| 测试方法 | 推断内容 |
|----------|----------|
| 输入对抗性内容 | 安全检测的实时性、防护层级 |
| 测试模糊指令下的行为 | 确定性边界、人工介入阈值 |
| 分析"可解释性" | 可解释性设计等级 |
| 测试长对话行为漂移 | 一致性维持机制 |

### Layer 5 铁律

**铁律 L5-01**：AI 逆向分析仅限公开可观察的行为推断，不得使用任何非法手段获取系统内部信息。

**铁律 L5-02**：Prompt 逆向的产出是"架构推断图"而非"Prompt 猜测"——推断其结构化组件（角色设定/输出格式/安全约束/工具描述/记忆策略）。

<a id="cross-validation"></a>
## 交叉验证矩阵

Step 7 战略整合时，必须执行以下交叉验证：

| 战略意图推断（L4） | 支撑证据来源 | 交叉验证结果 |
|-------------------|-------------|-------------|
| 意图 A | L1 证据: ___ / L2 证据: ___ / L3 证据: ___ | ✅ 一致 / ⚠️ 矛盾 |
| 意图 B | L1 证据: ___ / L2 证据: ___ / L3 证据: ___ | ✅ 一致 / ⚠️ 矛盾 |

**铁律 L7-01**：每个 Layer 4 的战略意图推断，必须有至少 2 个其他层的证据支撑，否则降级为 `[低置信]`。当不同层的证据指向矛盾方向时，**不得取平均值**，而必须深入分析矛盾原因——矛盾本身往往是最有价值的洞察。

<a id="credibility"></a>
## 信息源可信度分级

| 等级 | 来源类型 | 说明 |
|------|----------|------|
| ⭐⭐⭐ | 一手体验 | 自己使用产品、截图、录屏 |
| ⭐⭐ | 官方文档 | 帮助中心、官方博客、定价页 |
| ⭐ | 第三方信息 | 测评文章、知乎回答、媒体报道 |
| ⚠️ | 间接推断 | 基于其他信息源推断，必须标注 `[推断]` |

**视频/播客场景扩展**：

| 来源类型 | 可信度 | 说明 |
|----------|--------|------|
| 官方产品演示（官方 YouTube/发布会） | ⭐⭐⭐ | 等同于官方文档 |
| 官方播客/创始人访谈 | ⭐⭐⭐ | 战略意图的直接信号 |
| 官方帮助中心视频教程 | ⭐⭐⭐ | 功能真实流程的权威来源 |
| 知名第三方测评 | ⭐⭐ | 基于实际使用，但可能带有测评者立场 |
| 普通用户教程 | ⭐ | 真实性高但覆盖面有限 |

<a id="early-product"></a>
## 早期产品适配

对发布 < 6 个月的产品，Layer 3 的分析逻辑需要调整：

| 维度 | 成熟产品（>6 月） | 早期产品（<6 月） |
|------|-------------------|------------------|
| AARRR 分析重点 | 五环节全量分析 | 侧重 Acquisition + Activation，其他标注为"增长回路假设" |
| 增长回路 | 验证已存在的增长回路 | 提出增长回路假设，标注 `[假设]` |
| 数据来源 | DAU/MAU/留存率/付费转化率 | 社区讨论热度、版本更新频率、招聘方向 |
| 关键指标 | 定量指标（LTV/CAC/留存率） | 早期信号指标（见下表） |

### 早期信号指标库

| 信号指标 | 获取方式 | 指示方向 |
|----------|----------|----------|
| 社区讨论热度 | Reddit/V2EX/知乎/即刻 搜索产品名 | 市场关注度和口碑势能 |
| 版本更新频率 | GitHub Release / App Store 更新日志 | 团队投入度和迭代速度 |
| 招聘方向 | LinkedIn/拉勾/Boss直聘 搜索公司名+职位 | 下一步战略方向 |
| 创始人/高管访谈 | YouTube/B站/播客 搜索 | 战略意图的直接信号 |
| 竞品回应 | 竞品是否推出对标功能 | 该产品是否已对竞品构成威胁 |
| 集成生态 | MCP/Skill/插件市场活跃度 | 平台化进展 |

<a id="two-pass"></a>
## Two-Pass 增量修正协议

### Pass 2 输入类型体系

| 类型 | 内容 | 核心增强层 | 价值 |
|------|------|-----------|------|
| A. 截图/录屏 | 产品界面实际使用过程 | L1（交互架构）+ L0（产品身份验证） | 验证/推翻 L1 交互推断 |
| B. 视频/播客转录 | 官方演示/创始人访谈/第三方测评 | L5（AI 系统）+ L4（战略意图）+ L3（增长） | 大幅增强 Layer 5 可信度 |
| C. 工具链/推理链捕获 | Agent 思考过程、工具调用序列 | L5（AI 系统）——最具价值的输入 | 直接验证/推翻 Layer 5 推断 |
| D. 测试协议结果 | 执行测试协议 P-01~P-08 等的结果 | L5（测试协议验证）+ L1（交互验证） | 将 Layer 5 从"推断"升级为"已验证" |

### 增量标注协议

Pass 2 的所有修正必须使用标准化标注：

| 标注 | 含义 | 使用场景 |
|------|------|----------|
| `[Pass 2 新增]` | Pass 1 未涉及的新内容 | 新材料带来了全新的推断或事实 |
| `[Pass 2 修正]` | Pass 1 的推断被修正 | 新材料与 Pass 1 推断矛盾，且新材料更可信 |
| `[Pass 2 推翻]` | Pass 1 的核心推断被否定 | 新材料直接证伪了 Pass 1 的推断 |
| `[Pass 2 确认]` | Pass 1 的推断被强化 | 新材料支持 Pass 1 推断，置信度提升 |
| `[Pass 2 补充]` | 对 Pass 1 推断的细节补充 | 新材料增加粒度但不改变方向 |

### Pass 2 执行流程

```
触发条件：用户主动提供补充材料

Step 1: 输入分类与映射
  → 识别输入类型（A/B/C/D）
  → 映射到受影响层级
  → 标注输入可信度等级

Step 2: 受影响层重新分析
  → 用新材料替换/补充该层的原有证据
  → 保持"事实→推断"分栏格式
  → 新增推断必须标注 `[Pass 2 新增]`

Step 3: 交叉验证更新
  → 新材料是否与其他层的推断产生新矛盾？
  → 更新交叉验证矩阵

Step 4: 变更追踪生成
  → 对比 Pass 1 和 Pass 2 的差异
  → 按"新增 / 修正 / 推翻"分类标注

Step 5: 产出 v2 版本
  → 完整保留 Pass 1 内容（作为基线）
  → 追加 Pass 2 增量修正（独立章节）
  → 更新信息缺口和置信度
```

### Pass 2 设计原则

1. **Pass 1 永远是基线**：即使 Pass 2 推翻了 Pass 1，原始内容也必须保留
2. **用户输入 ≠ 绝对真理**：对新材料同样执行"事实→推断"分栏
3. **最小化用户负担**：Pass 1 后主动呈现"信息缺口报告"，针对性建议补充方向
4. **渐进式增强**：用户可分批提供材料，每次仅更新受影响的层
