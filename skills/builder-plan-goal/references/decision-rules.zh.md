# Builder Plan Goal 决策规则

使用这些规则判断一个请求应该用普通 Prompt、Plan、Goal、Plan -> Goal，还是先提问。

## 快速判断

按以下顺序判断：

1. 任务是否小到一次提示即可完成？
   - 是：普通 Prompt。
   - 否：继续判断。
2. 用户是否还没有说清目标、范围、上下文或验收？
   - 是：Plan 或先提问。
3. 是否已有清晰 Done when 和 Verification？
   - 是：Goal。
4. 是否涉及大范围重构、迁移、复杂产品原型、跨模块架构或多阶段交付？
   - 是：Plan -> Goal。
5. 是否缺少关键业务、安全、权限、数据迁移或生产风险决策？
   - 是：先提问。

## 普通 Prompt

适合：

- 简单问答、解释、翻译。
- 小范围文案、样式、单文件修复。
- 用户已经给出明确文件、改法和验收。

输出方式：

- 直接给一条清楚的普通指令，或说明“不需要 Plan/Goal”。

## Plan

适合：

- 需求模糊，需要澄清。
- 不熟悉代码库，需要先侦察。
- 有多种方案，需要比较取舍。
- 重构、迁移、架构、复杂 UI 或原型开始前。
- bug 原因不明，需要先建立诊断路径。

Plan 的完成标准：

- 范围清楚。
- 假设明确。
- 方案有比较。
- 里程碑可审查。
- 文件影响可预期。
- 验证策略可执行。
- 下一个 `/goal` 可以直接复制。

## Goal

适合：

- 目标清楚，边界明确。
- 需要多步执行，但最终结果可验证。
- 有测试、构建、截图、benchmark、复现步骤或人工 QA 标准。
- 单个 bug、单个页面、单个模块、单个重构里程碑。

Goal 的必要要素：

- Goal：结果契约。
- Context：必要上下文。
- Scope：允许和禁止范围。
- Done when：可判断完成标准。
- Verification：验证命令或人工检查。
- Stop condition：遇到阻塞时何时停止。

## Plan -> Goal

适合：

- 目标大，直接 Goal 容易失控。
- 需求还需要产品或架构收敛。
- 一次实现会产生不可审查的大 diff。
- 需要多个里程碑，每个里程碑单独验证。

推荐流程：

1. 用 `/plan` 获取实施蓝图、风险和 Milestone 1 `/goal`。
2. 用户评审并删减范围。
3. 用 `/goal` 只执行 Milestone 1。
4. 完成后 review diff、验证结果，再决定下一个 Goal。

## 先提问

当以下信息缺失且会改变实现方向时，先问不超过 3 个问题：

- 业务规则或验收标准。
- 数据来源、权限边界、安全约束。
- 是否允许改公共 API、数据库 schema、认证、生产配置。
- UI/产品原型的目标用户和核心流程。
- 重构是否允许行为变化。

提问方式：

- 优先给 A/B/C 选项，降低用户输入成本。
- 不要问已经能从上下文推断的问题。
- 不要把需求访谈变成冗长问卷。

## AI Builder OS Handoff 判断

当用户请求进入 AI Builder OS 构建链路时，按下列规则交接：

| 情况 | 推荐 handoff |
| --- | --- |
| 产品意图模糊，用户/场景/价值不清 | `builder-frame` |
| 已有 Feature Frame 或明确需求，需要形成可构建规格 | `builder-spec` |
| 请求页面、线框图、原型、视觉验证或交互流程 | `builder-prototype` |
| 要把任务交给 Codex / Claude Code / Qoder / Cursor / Workbuddy 执行 | `builder-agent-task` |
| 需要评审输出、证据、Go/No-Go、readiness | `builder-review` |
| 需要记录产品、架构、范围、发布或安全取舍 | `builder-decision` |

handoff 不替代 Plan/Goal 判断。复杂任务可以先 Plan，再把 Milestone 1 Goal 交给下游 skill 或 runtime。

## 风险信号

看到这些词时提高警惕：

- “完整系统”
- “全部重构”
- “顺便”
- “像某某产品一样”
- “企业级”
- “自动优化”
- “先做起来”
- “你看着办”
- “不要问我，直接做”
- “上线”
- “迁移生产数据”
- “改权限”

处理方式：

- 将宏大目标拆成 milestone。
- 明确本次不做什么。
- 要求 Done when 和 Verification。
- 对高风险缺口先提问。
