# Builder Plan Goal 反模式与修正

输出前必须检查这些失败模式。

## 反模式 1：把 Goal 当成更强普通 Prompt

坏例子：

```text
/goal 帮我把这个项目做好。
```

问题：

- 没有结果契约。
- 没有范围。
- 没有完成标准。
- 无法判断何时停止。

修正：

- 写清楚一个 milestone。
- 添加 Done when 和 Verification。
- 明确本次不做什么。

## 反模式 2：一个 Goal 承担完整系统

坏例子：

```text
/goal 做一个企业级新品上市 Agent 平台，包括登录、权限、数据库、流程编排、UI、测试和部署。
```

修正：

- 先 `/plan`。
- 拆成信息架构、第一屏、详情页、mock 数据、状态流转、测试和文档等 milestone。
- 每次只执行一个可审查资产。

## 反模式 3：Plan 只是待办清单

坏例子：

```text
/plan 列一下要做什么。
```

问题：

- 没有上下文侦察。
- 没有方案比较。
- 没有风险和验证。
- 不能直接转成 Goal。

修正：

- 要求当前现状、方案对比、文件影响、milestone、验证策略和 Milestone 1 `/goal`。

## 反模式 4：没有“不做什么”

问题：

- Agent 可能顺手改架构、加依赖、接数据库、做认证、改公共 API。

修正：

在提示词中加入：

```text
本次不做：
- 不新增认证/权限/数据库 schema。
- 不改公共 API。
- 不做无关重构。
- 不引入新依赖，除非必要且说明理由。
```

## 反模式 5：验收标准不可判断

坏例子：

```text
让页面更高级、更现代、更好用。
```

修正：

```text
Done when:
- 用户可以在 /launch-board 查看项目列表。
- 可以按阶段筛选。
- 可以打开项目详情。
- 每个阶段显示角色、Agent 输出和人工决策点。
- build 通过，桌面和移动端主要视口无明显重叠。
```

## 反模式 6：复杂任务不先 Plan

风险：

- 直接进入实现，导致范围漂移。
- 生成不可审查的大 diff。
- 把产品判断交给 agent。

修正：

- 对重构、迁移、架构、复杂产品原型，一律建议 Plan -> Goal。

## 反模式 7：把业务决策藏进提示词

风险：

- Agent 会替用户决定权限、流程、定价、合规、数据保留、生产配置。

修正：

- 若缺少这些决策，先提问。
- 问题不超过 3 个，优先给 A/B/C 选项。

## 反模式 8：过度触发

问题：

- 简单任务也被包装成 Plan/Goal，增加沟通成本。

修正：

- 单文件、小文案、小解释、明确小修复直接普通 Prompt。

## 反模式 9：只做 prompt 润色

问题：

- 只是把用户原话改得更漂亮，没有改变可执行性。

修正：

- 必须补齐模式建议、风险、工作流、Done when、Verification 和下一步。

## 反模式 10：handoff 不完整

问题：

- 只说“交给 builder-agent-task”，但没有传递目标、上下文、non-goals、验收标准和验证方式。

修正：

- handoff 至少包含：目标、上下文来源、推荐模式、关键假设、non-goals、验收标准、验证方式、停止条件。

## 输出前自检

- 是否推荐了最轻的有效模式？
- 是否解释了为什么不是其他模式？
- 是否指出当前最大风险？
- 提示词能否直接复制？
- 是否避免空泛词：完善、优化、企业级、高级、全面、智能化？
- 是否把大任务拆成可 review 的 milestone？
- 是否在缺少关键决策时停下来问问题？
- 是否明确 AI Builder OS handoff 目标和下游输入？
