## Layer 0：产品身份层

### 产品身份卡

| 维度 | 内容 |
|------|------|
| **一句话定义** | 面向全球中小企业的跨境电商 AI Agent 团队平台，30 分钟完成从创意到店铺上架的全流程 |
| **产品姿态** | **Sovereign**（主权型）—— 用户在完成跨境电商全流程时"住"在这个产品里，不是"用完即走"的工具 |
| **目标用户** | 显性：缺乏跨境经验的全球中小企业、独立创业者 / 隐性：阿里国际站的存量商家（做增量变现）/ 明确不服务：大型企业的复杂定制化需求 |
| **市场象限** | 高功能深度 + 中低价格 → "专业民主化"象限（把大企业才能做的事，让中小企业也能做） |
| **核心价值主张** | "一人 + AI = 五人跨境团队"——如果不做 AI Agent 协作，这个产品没有存在理由 |

### 前身关系（关键上下文）

```
Accio（2024.11 上线）
  → AI B2B 采购搜索引擎
  → 1000万+ 月活用户
  → 解决"找供应商"单一环节

Accio Work（2026.3.24 发布）
  → 从"搜索引擎"升级为"Agent 团队平台"
  → 覆盖建店→选品→采购→合规→营销→物流全链路
  → 战略意图：从"信息入口"升级为"运营平台"——锁定用户的全生命周期
```

> **[高置信] 推断**：Accio → Accio Work 的演进不是功能扩展，而是**商业模式升级**——从"帮用户找到供应商"（信息价值）到"帮用户做完整个跨境生意"（执行价值）。这从定价策略的演进也可见一斑（从免费搜索 → 积分制 Agent 执行）。

## Layer 1：交互架构层

### 五秒测试

> 打开 accio.com/work 首页，5 秒内感受到的核心印象：
>
> 1. **"AI Agent Team"**——不是"AI 助手"，是"团队"。这个措辞选择暴露了产品的核心叙事策略
> 2. **"Turn Ideas Into Profits"**——不是"提升效率"，是"创造利润"。从效率叙事切换到收益叙事
> 3. **本地优先桌面端**——强调数据安全，暗示企业级定位

> **[中置信] 推断**：从"助手"到"团队"的叙事切换，不是文案选择，而是**交互主权分配策略**的信号——产品将 AI 定位为"自主执行的团队成员"而非"等待指令的助手"。这意味着产品的核心交互模式是**AI 主导 + 人类审批**，而非人类主导 + AI 辅助。

### 导航解剖

根据官方教程和产品截图描述，Accio Work 的核心界面结构：

```
┌─────────────────────────────────────────────────────────┐
│ Accio Work                                              │
├──────────┬──────────────────────────┬───────────────────┤
│          │                          │                   │
│  会话列表  │      对话/执行区          │   技能/结果区      │
│          │                          │                   │
│  (历史)   │  输入商业目标             │  技能栏 [+添加]    │
│          │  → Agent 团队自动组建      │  执行进度可视化    │
│          │  → 并行执行 + 进度展示     │  产出物预览       │
│          │                          │                   │
├──────────┴──────────────────────────┴───────────────────┤
│  模型切换  │  语言设置  │  浏览器连接状态                    │
└─────────────────────────────────────────────────────────┘
```

**关键设计意图推断**：

| 设计决策 | 推断的意图 |
|----------|-----------|
| 右侧有独立的"技能栏"且可 `[+]` 添加 | 技能是可扩展的"能力层"而非固定功能——产品希望用户逐步构建自己的"兵器库"，增加切换成本和留存 |
| 对话区展示"Agent 团队自动组建"过程 | 让用户"看到"AI 在工作——这是**过程可见性**策略，降低用户对 AI 自主执行的焦虑 |
| 模型切换在底部而非顶部 | 模型是"基础设施"而非"核心交互"——产品不希望用户围绕模型选择来使用，而是围绕业务目标 |
| 浏览器连接是独立设置步骤 | 浏览器插件是 Agent 与外部世界交互的"手"——没有这个连接，Agent 就是"只说不做"的 |

### IA 逆向工程

```
Level 0: 商业目标输入（一句话描述你要做什么）
  ├─ Level 1: Agent 团队自动组建（系统决定需要哪些 Agent）
  │    ├─ Level 2a: 市场分析 Agent → 输出市场报告
  │    ├─ Level 2b: 选品 Agent → 输出产品推荐
  │    ├─ Level 2c: 店铺设计 Agent → 输出店铺模板
  │    ├─ Level 2d: 采购谈判 Agent → 输出供应商匹配
  │    ├─ Level 2e: 合规 Agent → 输出合规文件
  │    └─ Level 2f: 营销 Agent → 输出营销内容
  └─ Level 3: 高风险操作审批（人工确认点）
       └─ Level 4: Skill 封装（将流程固化为可复用技能）
```

> **[高置信] 推断**：IA 的核心逻辑是**"目标驱动 → 系统编排 → 人工审批"**，而非传统的"功能菜单 → 用户选择 → 逐步操作"。这意味着产品的设计哲学是**"AI 是主角，人是审批者"**——与传统工具的"人是操作者，AI 是辅助"完全相反。

### 反向用户旅程图

**核心旅程**：从"一个想法"到"一家跨境店铺上线"

| 步骤 | 用户行为 | 产品引导策略 | 设计意图 |
|------|----------|-------------|----------|
| 1 | 安装客户端 + 浏览器插件 | 保姆级教程（5 步引导） | 降低"第一步"的摩擦力——安装复杂度是 Agent 产品的最大流失点 |
| 2 | 输入商业目标/创意 | 极简输入框 + 示例提示 | 让用户"先开始"而非"先学会"——降低了认知门槛 |
| 3 | 观看 Agent 团队组建 | 自动展示每个 Agent 的角色和任务 | **过程可见性**：让用户理解"为什么需要这些 Agent"，建立信任 |
| 4 | 查看 Agent 并行执行 | 实时进度可视化 | 减少等待焦虑——AI 执行的不确定性是用户最大的恐惧 |
| 5 | 审批高风险操作 | 明确的确认弹窗 | **安全阀门**：让用户保持"控制感"，尽管大部分工作 AI 已自主完成 |
| 6 | 封装为 Skill | 引导用户保存成功的流程 | **留存钩子**：封装的 Skill 越多，切换成本越高 |

> **[高置信] 关键发现**：Accio Work 的交互架构核心是**"可见的自主性"**——AI 高度自主执行，但通过过程可视化和审批节点让用户保持控制感。这是一种精妙的平衡：既不过度自主让用户恐惧，也不过度依赖用户指令让 AI 显得无能。

## Layer 2：业务逻辑层

### 反向 JTBD

| 用户"雇佣"Accio Work 完成的"工作" | 工作类型 |
|-----------------------------------|----------|
| "我有一个产品想法，但不知道怎么开始跨境生意" | **功能性**：降低从 0 到 1 的门槛 |
| "我知道怎么做跨境，但一个人忙不过来" | **功能性**：用 AI 替代人力，扩展个体能力 |
| "我怕踩跨境合规的坑" | **情感性**：消除不确定性恐惧 |
| "我想让别人觉得我很专业" | **社交性**：专业形象维护 |

> **[高置信] 核心洞察**：Accio Work 的核心 JTBD 不是"提升效率"（那是结果），而是**"消除跨境生意的不确定性"**。一个人做跨境最大的恐惧不是"做得慢"，而是"不知道该做什么"和"怕做错"。AI Agent 团队解决的是"不确定性"而非"效率"。

> **[中置信] 风险信号**：供应商端存在**价值不对等**——AI 自主谈判会压缩供应商利润空间，且供应商的"付出"（价格透明化 + AI 谈判压力）可能超过"获得"（更多订单）。这是平台双边市场的经典张力，如果供应商感到被"压榨"，可能选择退出或降低服务品质。

### 商业模式画布逆向

| 维度 | 内容 | 推断的战略意图 |
|------|------|---------------|
| **客户细分** | 全球中小企业（尤其缺乏跨境经验者） | 从"小白"切入，向上扩展——小白用户的 LTV 更高（长期绑定） |
| **价值主张** | "一人+AI=五人团队"；30分钟建店 | 不是"降本增效"而是"从不可能到可能"——创造增量市场 |
| **渠道** | accio.com 官网 + 阿里国际站导流 | 利用现有 1000万+ MAU 的流量红利——这是竞品无法复制的 |
| **收入来源** | **[Pass 2 修正]** 免费额度（无需邀请码） + Token 付费模式（折扣力度大） | **[修正]** 原报告描述为"积分制（免费2000积分+每日30积分）/ Pro $9.99→$20/月"，多个新来源（chooseai.net 实测、ai-bot.cn 评测）确认为更简单的"免费额度 + Token 付费"模式。**双层变现**逻辑不变：免费额度是"上瘾诱饵"，Token 付费是"按需锁定" |
| **核心资源** | 阿里 20 年电商数据 + 150 万供应商 + 4 亿商品 | **数据-生态飞轮**：数据越丰富 → AI 越精准 → 用户越多 → 数据越多 |
| **关键活动** | Agent 编排 + 数据整合 + 合规管理 | 合规是"护城河活动"——100+ 市场合规规则的维护是竞品难以复制的 |
| **关键伙伴** | 阿里国际站、1688、AliExpress | 生态内协同——降低数据获取成本 |
| **成本结构** | 模型 API 成本 + 合规维护 + 供应商运营 | 模型成本下降趋势 → 长期利润率改善；合规成本是"护城河投入" |

### 业务规则逆向

| 规则 | 推断的战略意图 |
|------|---------------|
| **[Pass 2 修正]** 免费额度 + Token 付费（无需邀请码） | 注册零门槛 + 免费体验"上瘾" + Token 付费锁定——比积分制更透明，降低用户"被算计"的感知 |
| 高级模型（Opus 4.6）消耗 Token 更快 | 引导用户向付费转化——高级模型是"诱饵" |
| **[Pass 2 新增]** 异构模型组队（不同 Agent 可选不同模型） | 模型混搭是"多脑协作"的价值锚——让用户觉得不是在用一个模型，而是在组建一个"多脑团队" |
| **[Pass 2 新增]** 每个本地文件操作需明确授权 | 安全合规 + 降低法律风险——比"仅高风险操作审批"更保守，可能因为阿里对数据安全的极致要求 |
| Skill 可封装并可"变现" | 创造"技能生态"——从"平台提供能力"进化为"用户贡献能力"，形成网络效应 |
| **[Pass 2 新增]** 自定义 Skill 不能直接配置，只能通过聊天指令让 Agent 安装 | Skill 开放度有限——目前是"官方供给+口头安装"而非"自由市场"，这可能是早期控制质量的做法 |

> **[高置信] 核心发现**：**[Pass 2 修正]** 积分/定价制的演进历史——从 Pass 1 报告的"从'百分比+24h重置'到'2000积分+不重置'"修正为更简洁的**"免费额度 + Token 付费"**模式。核心战略方向不变——**先让用户上瘾（免费全量使用），再开始收费**——但形式比积分制更透明，暗示产品团队可能从"模糊成本感知"策略转向了"透明定价"策略。

## Layer 3：增长引擎层

### AARRR 逆向拆解

| 环节 | 机制 | 引擎/瓶颈判断 |
|------|------|---------------|
| **Acquisition（获客）** | 阿里国际站 1000万+ MAU 导流 + "30分钟建店"的病毒式传播 | **引擎**——阿里生态导流是零成本获客，这是竞品无法复制的 |
| **Activation（激活）** | 保姆级安装教程 + 极简"一句话启动" + 浏览器插件连接 | **潜在瓶颈**——安装浏览器插件是高摩擦步骤，可能造成大量流失 |
| **Retention（留存）** | Skill 封装（切换成本）+ **[Pass 2 修正]** Token 付费习惯（用得越多越依赖）+ 数据积累（越用越懂你） | **引擎**——Skill 封装是最强留存钩子：封装越多 → 切换成本越高 |
| **Referral（推荐）** | "30分钟建店"的炫耀式分享 + Skill 变现的创作者激励 | **潜在引擎**——如果 Skill 变现跑通，会形成创作者经济 |
| **Revenue（变现）** | **[Pass 2 修正]** 免费额度 + Token 付费 | **瓶颈**——Token 付费模式的折扣力度大，说明仍在寻找最优定价点 |

### 核心增长回路

```
                 ┌──────────────────────────────────────┐
                 │                                      │
                 ▼                                      │
  [阿里生态导流] → [新用户注册] → [免费额度体验] → [AI执行结果      │
                                        │        惊艳→信任]  │
                                        │           │       │
                                        ▼           ▼       │
                                   [Skill封装]  [分享/口碑]  │
                                        │           │       │
                                        ▼           ▼       │
                                   [切换成本↑]  [新用户进入] ─┘
                                        │
                                        ▼
                                   [Pro订阅转化]
```

> **[高置信] 增长引擎判定**：**生态驱动型增长**——核心燃料是阿里的流量和数据，不是产品本身的病毒式传播。这意味着增长天花板取决于阿里生态的覆盖范围，而非产品的市场渗透力。

### 行为锚点与留存机制

| 机制 | 类型 | 锚点 |
|------|------|------|
| 30 分钟建店 | **啊哈时刻** | "我居然真的能做到？"——从不可能到可能的震撼 |
| Skill 封装 | **沉没成本** | 封装的 Skill 越多，越不舍得换工具 |
| **[Pass 2 修正]** Token 付费 | **渐进锁定** | 用得越多 → 付费习惯形成 → 越依赖平台 |
| 浏览器插件连接 | **锁入机制** | 安装插件是高摩擦操作，用户不愿重复——反而成为留存 |
| 数据积累 | **学习效应** | AI 对用户的业务理解越来越深——"换工具 = 从零开始" |

## Layer 4：战略意图层

### 时间旅行分析

| 时间节点 | 事件 | 推断的战略决策 |
|----------|------|---------------|
| 2024.11 | Accio 上线（AI 采购搜索引擎） | 进入"信息层"——先做"找供应商"这个最高频的跨境痛点 |

| 2026.3 | 同时推出 Wukong（企业编排层） | **双线战略**：Accio Work 做 SMB 单体，Wukong 做企业多 Agent 编排 |

> **[高置信] 战略方向推断**：Accio → Accio Work → Wukong 的演进路线图清晰可见——
> **信息入口 → 执行平台 → 企业基础设施**。这是经典的"工具 → 平台 → 生态"三步走。

### 负空间分析（"没有做什么"）

| 没有做什么 | 推断的战略考量 |
|-----------|---------------|
| **没有开放 API** | **[Pass 2 修正]** 此判断需要修正——Accio Work 通过 OpenClaw 框架开放了 Skill 生态，GitHub 上有开源的 AccioWork/agent-skills 仓库，技能通过 accio.com API 实时获取数据。但核心的 Agent 编排引擎和底层数据访问确实未开放——"开放的是技能层，封闭的是编排层" |
| **没有做通用办公场景** | 聚焦跨境垂直——通用场景有 WorkBuddy/Copilot 竞争，垂直场景可以建立数据壁垒 |
| **没有做中国国内市场** | 目标是全球 SMB——国内市场的跨境需求可以由阿里国际站直接覆盖，无需 Agent |
| **没有做移动端原生 App** | 选择桌面端 + 浏览器插件——Agent 需要操作本地文件和浏览器，移动端执行能力受限 |
| **没有开源** | 数据和算法是核心壁垒——开源等于把护城河的砖拆给别人 |

> **[高置信] 最关键的负空间**：Accio Work **没有做"通用 Agent"**。这不是能力不足，而是**刻意选择**——通用 Agent 市场（Cursor/Copilot/WorkBuddy）竞争激烈，而跨境垂直 Agent 几乎没有同量级竞品。这是一个"避开主战场，在侧翼建立根据地"的经典策略。

## Layer 5：AI 系统逆向层

> **⚠️ 声明**：以下分析基于公开可观察的产品行为和官方描述的推断，未使用任何非法手段获取系统内部信息。所有推断标注置信度。

### Prompt 架构推断

基于产品行为观察：

| 观察到的行为 | 推断的 Prompt 组件 |
|------------|-------------------|
| 输入一个商业目标后自动组建 Agent 团队 | **编排 Prompt**：包含"根据用户目标选择合适 Agent 角色并分配任务"的指令 |
| Agent 之间并行执行且结果互不干扰 | **隔离 Prompt**：每个 Agent 有独立的 System Prompt 和上下文边界 |
| 高风险操作需人工确认 | **安全约束**：Prompt 中嵌入"涉及财务/法律/文件操作时暂停并请求确认"的规则 |
| 输出与阿里国际站数据强相关 | **知识注入**：Prompt 中注入了阿里电商数据结构、供应商匹配逻辑 |
| 支持中英文切换且输出质量一致 | **多语言适配**：Prompt 支持动态语言切换，而非翻译层 |

### Harness Engineering 解构

| 维度 | 观察到的行为 | 推断的 Harness 设计 |
|------|------------|-------------------|
| **工具暴露** | 浏览器插件操控 + 阿里数据API + 文件生成（PPT/报告） | 工具设计是**垂直专用**而非通用——每个工具绑定特定电商场景 |
| **错误恢复** | 官方教程中强调"安装浏览器插件是最关键一步" | 浏览器连接是单点故障——插件断开 = Agent 失去"手" |
| **上下文管理** | Agent 团队并行执行但共享用户目标 | **分形上下文**：共享高层目标 + 独立子任务上下文——避免 Agent 间信息干扰 |
| **权限边界** | 高风险操作（财务/法律/文件）需人工确认 | 两级权限模型：低风险自主执行 + 高风险人工审批——这是"AI主导 + 人类审批"主权模式的具象化 |
| **并发行为** | 多 Agent 并行执行（市场分析+选品+建店同时进行） | DAG 调度模式——有依赖关系的任务串行，无依赖的并行 |
| **输出验证** | 生成的店铺/商品可"直接复制粘贴到国际站后台" | 输出格式严格匹配阿里国际站的数据结构——这是"格式校验"而非"内容校验" |

### 交互主权分析

| 维度 | Accio Work 的选择 | 推断 |
|------|-------------------|------|
| **默认主权模式** | AI 主导 + 人类审批 | 产品对 AI 能力有高信心，且目标用户（跨境小白）更需要"AI 帮我做"而非"AI 教我做" |
| **主权切换** | 无显式切换 | 不提供"用户主导"模式——暗示产品的核心价值在"AI 自主执行"而非"AI 辅助" |
| **审批粒度** | 仅高风险操作 | 大部分操作 AI 自主完成——减少人工干预以体现"Agent 团队"而非"AI 助手"的价值 |

### Eval 体系推断

| 观察方法 | 推断内容 |
|----------|----------|
| 输出格式与阿里国际站后台数据结构严格匹配 | 有**格式 Eval**——输出必须符合特定的数据结构才能"直接复制粘贴" |
| 合规建议必须标注"非法律意见" | 有**安全 Eval**——法律相关输出必须包含免责声明 |
| 高风险操作需人工确认 | 有**风险分类 Eval**——系统会判断操作的风险等级并决定是否需要人工介入 |
| 30 分钟建店的成功率被官方宣传 | 可能有**端到端 Eval**——衡量从输入到成功上架的完成率 |
| Skill 可封装并可复用 | 可能有**流程质量 Eval**——评估封装的 Skill 是否能稳定复现结果 |

> **[低置信] 注意**：以上 Eval 推断基于间接证据。Accio Work 的 Eval 体系可能是产品内部最不成熟的部分——因为 Agent 编排的确定性本身就很难保证，而跨境场景的"正确答案"比编程场景模糊得多。

## 差异化作战地图

### 他们的"负空间"（Accio Work 不做什么）

| 负空间 | 为什么是机会 | 切入策略 |
|--------|-------------|---------|
| **只做跨境，不做其他垂直** | 跨境是一个场景，但"垂直行业 Agent 平台"是一个品类 | 做"行业 Agent 平台的基础设施"——让任何行业都能像 Accio Work 一样快速构建垂直 Agent |
| **只做阿里生态，不开放** | 生态封闭 = 用户绑定 = 用户恐惧 | 做"开放生态 Agent 平台"——支持任意数据源和工具接入 |
| **不做通用工作流编排** | 用户的不同业务场景之间有共性工作流 | 做"跨行业可迁移的工作流编排层"——将 Accio Work 的模式泛化 |
| **不做移动端原生** | 移动端是 Agent 的下一个主战场 | 做"移动端优先的 Agent 体验"——通过 IM 触达（微信/WhatsApp） |
| **没有做 Skill 市场验证** | Skill 变现是未验证的假设 | 做"已验证的技能市场"——先跑通创作者经济再扩张 |

### 我们的"奇兵"

| 奇兵方向 | 为什么 Accio Work 不会做 | 怎么做 |
|----------|------------------------|--------|
| **通用 Agent 编排引擎** | 他们选择垂直绑定以获取数据优势 | 做横向——"任何行业的 Accio Work"，用开放性对抗数据深度 |
| **跨行业 Skill 市场** | 他们的 Skill 只在电商场景有值 | 做跨行业——"AI 版 App Store"，一个 Skill 在医疗/金融/教育都能用 |
| **人类主导模式** | 他们选择了 AI 主导，小白用户需要 | 做"专业用户版"——让有经验的人用 AI 增强而非替代 |
| **企业级 Agent 治理** | 他们的企业版（Wukong）尚未成熟 | 做企业级——Agent 权限/审计/合规/成本管控 |

### 切入路径

```
Phase 1: 从 Accio Work 的"负空间"切入
  → 做通用 Agent 编排引擎 + 开放 Skill 市场
  → 目标：吸引被 Accio Work 生态排斥的"非电商用户"

Phase 2: 从"工具"进化到"平台"
  → 开放 API + Skill 创作者经济
  → 目标：让用户贡献能力，形成网络效应

Phase 3: 从"平台"进化到"标准"
  → 定义 Agent 互操作标准
  → 目标：让其他 Agent 产品都兼容我们的 Skill 和编排协议
```

## 框架验证：问题与改进建议

> 以下是在实战应用中发现的框架问题，对应 pm-teardown v1.0 的改进方向

### 问题 1：Layer 0-1 的信息采集受限于"封闭产品"

**现象**：Accio Work 的官网和帮助文档内容极度稀薄（JS 渲染的 SPA 页面，WebFetch 只能获取标题），导致 Layer 0 和 Layer 1 的大量分析不得不依赖第三方信息源而非一手体验。

**改进**：
- 增加**"信息源可信度分级"机制**：一手体验 > 官方文档 > 第三方测评 > 社区讨论 > 推断
- 增加**"信息缺口标注"**：明确标注哪些维度的数据缺失，而非用推断填补
- 建议 Skill 中加入**"如果目标产品是桌面端 App，优先引导用户进行 5 秒测试和导航解剖的实际操作"**

### 问题 2：Layer 5 的 AI 逆向分析缺乏"可操作测试协议"

**现象**：报告中 Layer 5 的大部分内容是"推断"而非"测试结果"，因为缺乏具体的测试操作协议。例如"边界输入测试"和"角色泄漏测试"只是方法论描述，没有具体的测试用例。

**改进**：
- 为 Layer 5 增加**"AI 逆向测试协议库"**——包含 20+ 个标准测试用例（边界输入、角色泄漏、一致性测试等），每个测试用例有具体的输入模板和预期输出
- 区分**"可远程执行"**（通过 Web 界面）和**"需本地安装"**（桌面端 App）的测试——前者可以自动化，后者需要引导用户操作

### 问题 3：五层之间的"交叉推断"不够系统化

**现象**：报告中虽然每层都有推断，但层与层之间的交叉验证是手动进行的，缺乏系统化的交叉推断机制。

**改进**：
- 增加**"交叉验证矩阵"**：每个 Layer 4 的战略意图推断必须至少有 2 个其他层的证据支撑
- 增加**"矛盾信号检测"**：当不同层的推断指向不同方向时，自动标注并深入分析

### 问题 4：产出中"推断"和"事实"的边界不够清晰

**现象**：部分推断标注了置信度，但仍有大量内容是"事实+推断"的混合叙述，读者难以区分。

**改进**：
- 所有产出内容采用**"事实 → 推断"的分栏格式**：左侧是可验证的事实，右侧是基于事实的推断
- 每个 `[推断]` 必须标注**证据来源**和**推断逻辑**，而非仅标注置信度

### 问题 5：缺少"竞品横向对比"的轻量模式

**现象**：五层框架是纯纵向的，但在实际分析中，用户经常需要"Accio Work vs WorkBuddy"的快速对比。Deep Dive 模式太重，Rapid Scan 又太浅。

**改进**：
- 增加**"Layer 0 横向对比"模式**：对 2-3 个竞品同时做 Layer 0 + 关键差异点对比，5 分钟产出

#### 问题 9：截图揭示了大量"未在公开信息中出现"的功能

- 建立**"功能发现清单"**：对截图进行系统性扫描（导航项、按钮、标签、表单字段），确保不遗漏任何可见功能

**现象**：Agent 创建向导中的模型选择（4 个）与 Pass 2 报道的"异构模型组队"（5+ 个）不一致。可能是：

**改进**：
- 增加**"版本敏感性标注"**：所有发现标注产品版本/截图日期

**现象**：截图中的 TaskCreate→Read→Bash→WebSearch→Browser 链是极其宝贵的 Harness Engineering 证据，但框架没有专门的章节来系统分析这种"可视化推理链"。

### 一、Layer 2 重大修正：权限与安全体系

#### 1.1 权限策略四层体系 [修正]

**Pass 1-3 判断**："两级权限模型（低风险自主执行 + 高风险人工审批）"
**Pass 4 修正**：**四策略权限体系**，远比推断的精细

| 策略 | 行为 | 等价概念 |
|------|------|----------|
| **Allow（允许）** | 直接执行，无需确认 | 类 Linux `chmod +x` |
| **Ask（问）** | 每次执行前都需要确认 | 类 UAC 弹窗 |
| **Ask Once（询问一次）** | 第一次询问；批准后，稍后自动运行 | 类"信任此开发者" |
| **Deny（否认）** | 总是拒绝；Agent 无法执行此操作 | 类防火墙黑名单 |

**按操作类型划分的默认策略** [Pass 4 确认]：

| 操作类型 | 默认策略 | 对比 Pass 1-3 推断 |
|----------|----------|-------------------|
| 文件读取 | ✅ Allow | [修正] 之前判断"通常允许"，确认 |
| 网络接入 | ✅ Allow | [修正] 之前判断"通常允许"，确认 |
| 文件写入 | ⚠️ Ask | [修正] 之前判断"高风险操作需人工确认"，过于笼统——实际是"Ask"而非"Deny" |
| Shell 执行 | ⚠️ Ask | [修正] 同上 |
| 浏览器使用 | ⚠️ Ask | [修正] 同上 |

> **[高置信] 关键修正**：权限模型不是"二元"的（自主 vs 审批），而是**四层递进**的——Allow / Ask / Ask Once / Deny。这意味着 Accio Work 的安全架构比我们判断的更成熟，接近企业级权限管理系统的设计水平。

#### 1.2 权限有效期 [Pass 4 新增]

| 持续时间 | 描述 | 推断 |
|----------|------|------|
| **一次** | 仅对当前操作有效 | 一次性授权——最安全但最烦 |
| **会话** | 对当前会话有效 | 会话级缓存——平衡安全和效率 |
| **持续** | 永久有效，直至手动撤销 | 类"始终信任"——最高效率但有安全风险 |

> **[高置信] 推断**：三种有效期是**安全性 vs 效率性的三档**——一次（最安全）、会话（平衡）、持续（最高效）。用户可以逐步从"一次"升到"持续"，这实际上是一个**信任建立机制**：让用户从"事事确认"逐步过渡到"放心让 AI 做"。

#### 1.3 白名单与目录保护 [Pass 4 新增]

**可信命令白名单**：
- 支持 `npm test`、`npm run build` 等常用安全命令自动批准
- 用户可自定义白名单

**敏感目录阻止**：
- 可创建 Deny 规则限制特定工具和路径前缀
- 示例：禁止对 `/etc` 的所有写入

**工作区边界保护**（3 层控制）：

| 控制 | 作用 | 推断 |
|------|------|------|
| **路径允许列表** | 限制哪些目录可以访问 | 类沙盒文件系统白名单 |
| **符号链接保护** | 防止通过符号链接绕过限制 | 防御性安全设计——防止 symlink 攻击 |
| **边界检查** | 确保所有文件操作都在 workspace 内 | 最终兜底——任何路径操作必须验证边界 |

> **[高置信] 推断**：三层工作区边界保护表明 Accio Work 对**沙盒隔离**的重视程度极高——不是简单的"根目录限制"，而是防御了 symlink 绕过等高级攻击向量。这可能是阿里安全团队的要求——阿里对数据安全有极致要求（参考阿里云等保合规）。

#### 1.4 审核日志 [Pass 4 新增]

- 所有权限决策（自动或手动）都记录在审核日志中
- 用户可查看 Agent 尝试了什么、批准了什么、拒绝了什么

> **[高置信] 推断**：审核日志是**企业级合规的刚需**——没有审计日志，Agent 平台不可能进入企业市场。这说明 Accio Work 从第一天就在为 Wukong 企业版做架构准备。

#### 1.5 权限体系对差异化作战地图的影响

Pass 1-3 的差异化判断之一是"企业级 Agent 治理"是 Accio Work 的负空间。**Pass 4 修正**：Accio Work 的权限体系已经达到了企业级水准——四策略 + 三有效期 + 白名单 + 目录保护 + 审核日志。这意味着"企业级治理"的差异化窗口**比之前判断的更小**。

### 二、Layer 5 重大发现：agent-core 架构——与 WorkBuddy 几乎同构

> ⚠️ **这是整个拆解报告中最重要的发现之一。**

#### 2.1 agent-core 目录结构 [Pass 4 新增]

**官方文档描述**：每个 Agent 都有一个 `agent-core` 目录作为其"大脑"。

| 文件/文件夹 | 目的 | WorkBuddy 对应物 | 同构性 |
|------------|------|-----------------|--------|
| **SOUL.md** | 定义 Agent 的角色和行为边界 | `SOUL.md`（工作区根目录） | ✅ 完全同构 |
| **IDENTITY.md** | 定义 Agent 的身份和沟通风格 | `IDENTITY.md`（工作区根目录） | ✅ 完全同构 |
| **AGENTS.md** | 行为指南和工作原则 | 无直接对应（WorkBuddy 将此逻辑嵌入 SOUL.md） | ⚠️ 部分同构 |
| **MEMORY.md** | 重要跨会话信息的长期记忆 | `MEMORY.md`（.workbuddy/memory/） | ✅ 完全同构 |
| **USER.md** | 记录用户偏好和背景的用户个人资料 | `USER.md`（工作区根目录） | ✅ 完全同构 |
| **BOOTSTRAP.md** | 初始化说明 | `BOOTSTRAP.md`（工作区根目录） | ✅ 完全同构 |
| **TOOLS.md** | 可用工具列表 | 无直接对应（WorkBuddy 通过 MCP/内置工具提供） | ❌ Accio 独有 |
| **tool-registry.jsonc** | 工具注册配置 | 无直接对应（WorkBuddy 的工具注册在 mcp.json） | ❌ Accio 独有 |
| **diary/** | 工作日记目录 | `.workbuddy/memory/YYYY-MM-DD.md`（日志模式） | ⚠️ 概念同构，实现不同 |
| **skills/** | 私有技能包目录 | `.workbuddy/skills/` | ✅ 完全同构 |

> **🔥 [极高置信] 核心发现**：Accio Work 和 WorkBuddy 的 Agent 身份管理系统**独立收敛到几乎完全相同的架构**——SOUL.md / IDENTITY.md / MEMORY.md / USER.md / BOOTSTRAP.md / skills/ 这 6 个核心组件**一对一映射**。
>
> 这不是巧合——这说明**持久化 AI Agent 的"自然架构"已经浮现**：每个 AI Agent 需要（1）灵魂/身份定义、（2）跨会话记忆、（3）用户认知、（4）初始化协议、（5）可扩展能力。任何做"持久化 Agent"的产品都会收敛到这个架构。
>
> **战略含义**：这种架构收敛意味着——
> - **差异化不在架构层，而在执行层**——两者的"灵魂"结构相同，但"行为"差异巨大
> - **Skill/工具生态是真正的差异化战场**——同构的 Agent 可以装不同的"武器"
> - **数据格式互操作的可能性**——理论上，Accio Work 的 SOUL.md 可以被 WorkBuddy 读取（反之亦然），因为结构相同

#### 2.2 上下文组装顺序 [Pass 4 新增]

**官方文档描述**：Agent 启动时，系统分三个阶段组装上下文。

| 阶段 | 加载顺序 | 推断的设计意图 |
|------|----------|--------------|
| **前缀** | IDENTITY.md → AGENTS.md | 先建立"我是谁"+"我应该怎么行为"——身份优先 |
| **中** | TOOLS.md → Skills → Workspace → Environment → Team context | 再加载"我有什么工具"+"我在什么环境"——能力其次 |
| **后缀** | MEMORY.md → SOUL.md → USER.md | 最后加载"我知道什么"+"我的灵魂"+"我服务谁"——记忆和约束最后 |

> **[高置信] Prompt Engineering 逆向**：
> - **前缀在前**：Identity 和行为规则先加载，确保后续所有工具使用和记忆回忆都"在角色中"
> - **中间是工具链**：工具和能力在身份之后加载——Agent 先知道"我是谁"再知道"我有什么"
> - **后缀在后**：MEMORY → SOUL → USER 的顺序极为精妙——先回忆知识，再用灵魂约束行为，最后对齐用户需求。这防止了"记忆中的信息被没有灵魂约束地使用"
> - **SOUL.md 在后缀而非前缀**：这意味着 SOUL.md 更像"行为约束/价值观"而非"角色定义"——角色在 IDENTITY.md 中，约束在 SOUL.md 中

#### 2.3 Agent 模板沟通风格 [Pass 4 确认 + 扩展]

**Pass 3 截图**：Vibe 系统有 6 种风格（Professional/Friendly/Creative/Concise/Casual/Expert）
**Pass 4 官方文档**：模板有 4 种默认沟通风格

| 模板 | 沟通方式 | 对应 Vibe | 推断 |
|------|----------|-----------|------|
| **Coder（编码员）** | 更加简洁、直接；更喜欢通过代码说话 | Concise / Expert | 代码优先，文档最小化 |
| **Product Manager（产品经理）** | 更加结构化；充分利用表格和列表 | Professional | 结构化输出是 PM 的核心能力 |
| **Reviewer（审稿人）** | 更注重风险和可维护性 | Expert（风险导向） | 安全审计视角 |
| **Daily Assistant（日常助理）** | 通用、友好、适应性强 | Friendly / Casual | 默认的通用 Agent |

> **[高置信] 推断**：模板的沟通风格与 Pass 3 截图中的 Vibe 系统是**同一系统的两个面**——模板预设了默认 Vibe，用户可在创建时修改。4 种模板 vs 6 种 Vibe = 模板是"预设配置"，Vibe 是"可调参数"。

#### 2.4 缓存机制 [Pass 4 新增]

- 核心文件通常缓存约 30 秒，提高响应速度
- 编辑文件时缓存自动失效，更改在下一次交互时生效

> **[中置信] 推断**：30 秒缓存意味着 agent-core 文件是**热加载**的——Agent 不需要重启就能读取修改后的文件。这是"实时调试 Agent"的基础——开发者可以随时修改 SOUL.md 并立即看到效果。

#### 2.5 Agent 间内存隔离与 SubAgent [Pass 4 新增]

| 规则 | 详情 |
|------|------|
| **Agent 隔离** | 每个 Agent 的记忆、灵魂和技能都是独立的——编辑一个 Agent 的核心文件不会影响任何其他 Agent |
| **SubAgent 例外** | SubAgent 共享父级 Agent 的核心目录，但通常**不修改**父级的长期记忆 |

> **[高置信] 架构推断**：SubAgent 机制揭示了一种**分层 Agent 架构**——
> - 父 Agent 拥有完整的 agent-core（灵魂+记忆+技能）
> - SubAgent 继承父 Agent 的核心目录（只读共享），但有自己的执行上下文
> - SubAgent 不能修改父级长期记忆——这是**"子进程不能修改父进程内存"**的 AI 等价物
>
> 这与 Pass 2 发现的"三省六部制"和"Team Leader 模式"呼应——TL Agent 可能就是通过 SubAgent 机制来协调多 Agent 协作的。

### 三、Layer 2-5 新增：智能体自我进化机制

#### 3.1 自我进化能力矩阵 [Pass 4 新增]

| 能力 | 描述 | 已有覆盖 | 战略意义 |
|------|------|----------|----------|
| **记住重要信息** | 自动检测值得保存的内容并写入内存文件 | Pass 3 提及"技能内存" | 记忆是 Agent 持久性的基础 |
| **了解用户偏好** | 通过互动了解工作风格和习惯 | Pass 1 提及"数据积累" | 个性化 = 切换成本 |
| **积累领域知识** | 随着任务积累变得更加专业 | 未明确覆盖 | **领域专业化是留存飞轮** |
| **学习新技能** | 将重复工作方式转变为可复用技能 | Pass 1 提及"Skill 封装" | Skill = 生态锁定的核心 |

#### 3.2 长期记忆工作机制 [Pass 4 确认 + 细化]

**官方文档描述的机制**：
1. 系统自动检测值得保存的信息
2. 当上下文接近 Token 限制时，Agent 会**主动**将重要内容写入内存文件
3. 新对话开始时，记忆文件作为上下文的一部分重新加载

> **[高置信] 关键发现**：Agent 在上下文接近 Token 限制时**主动**写入内存——这不是被动的"保存按钮"，而是**自动记忆管理**。这意味着 Accio Work 的 Agent 有"遗忘焦虑"——在上下文溢出前主动保存重要信息，类似人类在紧张时"赶紧记下来"的行为。

#### 3.3 加速进化的用户引导 [Pass 4 新增]

官方文档列出了 5 种加速 Agent 进化的方式：

| 方式 | 描述 | 已有覆盖 | 对产品设计的启示 |
|------|------|----------|-----------------|
| **主动分享背景** | 告诉 Agent 角色、行业和常用工具 | Pass 3 Step 5 User Profile | 产品应引导用户主动输入背景 |
| **维护用户档案** | 帮助 Agent 更快了解你 | Pass 3 Step 5 User Profile | USER.md 的持续维护是关键 |
| **立即提供反馈** | 直接告诉 Agent 哪些好/不好 | 未覆盖 | 需要轻量级反馈机制 |
| **巩固重复工作流** | 将重复任务转化为技能 | Pass 1 Skill 封装 | "检测重复"→"建议封装"是关键 UX |
| **定期回顾记忆** | 检查并纠正记忆内容 | 未覆盖 | 记忆审核 = 数据质量保障 |

> **[中置信] 推断**：这 5 种方式是 Accio Work 的**"Agent 养成指南"**——它实际上在教用户如何当一个好的"Agent 管理者"。这是**从"使用 AI"到"管理 AI"**的范式转变——用户不再是"操作工具的人"，而是"培养 AI 员工的经理"。

#### 3.4 自我进化安全机制 [Pass 4 新增]

| 安全机制 | 描述 | 对比 |
|----------|------|------|
| **Agent 隔离** | 不同 Agent 不共享内存 | 类进程隔离 |
| **用户控制** | 可随时检查、编辑或清除内存 | 类数据主权 |
| **透明变化** | 当 Agent 更新 SOUL.md 时，会**主动通知**用户 | 类 Git commit notification |
| **删除聊天 ≠ 删除记忆** | 删除聊天只删除该会话的上下文，长期记忆可能保留 | 类"清除聊天记录 ≠ 清除云备份" |

> **[高置信] 关键发现**："Agent 更新 SOUL.md 时主动通知用户"——这是一个**极其重要的安全设计**。SOUL.md 是 Agent 的"行为宪法"，如果 Agent 可以悄悄修改自己的灵魂而不告诉用户，那就可能出现"AI 自主修改行为约束"的风险。主动通知 = **灵魂修改的可审计性**。

| 层级 | 存储 | 生命周期 | 检索方式 |
|------|------|----------|----------|

#### 4.2 /dream 整合机制 [Pass 4 新增]

> ⚠️ **这是 Accio Work 最独特的创新之一——目前没有其他主要 AI 产品有类似功能。**

**官方描述**：
- /dream 整理短期记忆、diary/ 和 MEMORY.md 中的内容
- 典型行动：Promoting（短期→日记）、Distilling（日记→长期）、修剪（删除陈旧/冗余）

| /dream 运行方式 | 描述 | 推断 |
|-----------------|------|------|
| **手动** | 在操作面板输入 `/dream` | 用户主动触发记忆整理——类"睡前回顾" |
| **自动** | 每个日历日向指定 Agent 发送第一条消息时，类似通行证在后台运行 | 每日首次对话自动触发——类"晨间整理" |
| **信用消耗** | 非常低（按客户显示的确切成本） | 记忆整理的 Token 消耗极低——可能在用小模型处理 |

**/dream 三步操作**：

```
Step 1: Promoting（提升）
  SQLite 短期行 → diary/ 日记文件
  判断标准：使用频率、重要性标记

Step 2: Distilling（蒸馏）
  diary/ 日记内容 → MEMORY.md 长期文件
  判断标准：跨日相关性、主题归纳

Step 3: Pruning（修剪）
  删除陈旧或冗余的内容
  判断标准：时间衰减、重复检测
```

> **[极高置信] 战略级发现**：/dream 是**AI Agent 的"睡眠整理"机制**——人类在睡眠中巩固记忆（短期→长期）、删除无用信息。Accio Work 用 /dream 实现了 AI 等价物。
>
> **为什么这是战略级创新**：
> 1. **解决了"上下文窗口有限"的根本问题**——不是用更大的窗口，而是用记忆管理
> 2. **每日自动运行 = Agent 的"新陈代谢"**——不整理的 Agent 会"记忆膨胀"，整理的 Agent 保持精简高效
> 3. **极低信用消耗 = 可持续**——记忆整理不会成为用户的成本负担
> 4. **WorkBuddy 没有等价功能**——WorkBuddy 的记忆是"手动维护"的（用户/Agent 编辑 MEMORY.md），没有自动整理

#### 4.3 记忆访问的两种方式 [Pass 4 新增]

| 访问类型 | 触发时机 | 机制 | 类比 |
|----------|----------|------|------|
| **Agent 发起的内存搜索** | 执行任务时，Agent 决定何时搜索 | Agent 主动从 SQLite 提取相关片段 + agent-core 下约定的路径（如日记文件） | 类"主动回忆"——我需要什么信息，就去查找 |
| **自动会话调用** | 用户发送消息时，满足触发条件 | 客户端从 SQLite 拉取相关短期行，合并到当前回合上下文 | 类"联想记忆"——你说了一句话，我自动想到相关上下文 |

> **[高置信] 推断**：两种访问方式暗示了**双通道记忆检索**——Agent 既有"按需查找"（精确但慢），也有"自动联想"（模糊但快）。自动会话调用特别值得关注，因为它的"触发条件"是黑盒——用户不知道什么会触发什么记忆被召回，这可能导致"意外回忆"（类似人类的"触景生情"）。

### 七、框架验证：Pass 4 新增问题

#### 问题 12：官方文档与产品界面的信息互补模式

**现象**：4 份官方文档提供了截图无法展示的内部架构信息（agent-core 结构、上下文组装顺序、/dream 机制），而截图提供了文档没有展示的 UI 细致布局。两者互补性极强。

**改进**：
- 在 Skill 中增加**"文档优先于截图，截图优先于评测"**的信息源优先级：官方文档 > 产品截图 > 第三方评测 > 社区讨论
- 增加**"信息源互补清单"**：明确标注每种信息源能提供什么、不能提供什么

#### 问题 13：架构同构现象的系统性分析方法缺失

**现象**：Accio Work 和 WorkBuddy 的 agent-core 架构几乎同构是偶然发现的，而非系统性分析的结果。框架没有"竞品架构同构检测"的方法论。

**改进**：
- 增加**"架构同构检测"**章节：对比两个产品的核心文件结构、命名规范、加载顺序
- 建立**"自然架构假说"**：如果多个独立产品收敛到相同架构，说明这是该品类的"自然架构"——值得总结为标准

#### 问题 14：/dream 类"自主行为"的安全评估方法缺失

**现象**：/dream 是 Agent 的"自主记忆整理"行为——Agent 在没有用户指令的情况下修改自己的记忆文件。这带来了新的安全维度：如果 /dream 的蒸馏逻辑有偏，可能导致 Agent "遗忘"重要信息或"扭曲"记忆。框架没有评估这种"自主行为安全性"的方法。

**改进**：
- 在 Layer 5 增加**"自主行为安全评估"**子章节：评估 Agent 在无用户指令时的自主行为（记忆整理、自我进化、SOUL.md 修改通知）的安全性
- 建立**"自主行为审计"**清单：评估 Agent 自主行为的（1）可观测性、（2）可逆性、（3）可配置性
