# Builder 质量门禁

## 必需门禁

| 门禁 | 检查问题 | 失败处理 |
| --- | --- | --- |
| Intent Gate | 是否知道用户真正想要的结果？ | 回到意图澄清 |
| Scope Gate | 是否知道范围内外分别是什么？ | 执行前先收窄范围 |
| Asset Gate | 是否有明确产物或结果？ | 先定义输出契约 |
| Evidence Gate | 完成状态是否可验证？ | 降级为 `PARTIAL` 或转入 Plan |
| Anti-Rationalization Gate | 是否在用推断、疲惫、局部证据或 agent 自报替代验证？ | 停止完成声明，补证据或降级状态 |
| Handoff Gate | 结果是否能被下一步消费？ | 补 Output Packet |

## 规则

如果门禁失败，不要假装完成。应该修复、提问，或报告阻塞条件。

## Red Flags

出现以下信号时，必须停下并回到 Evidence Gate 或 Scope Gate：

- 使用“应该、可能、看起来、理论上、差不多”等词支撑完成状态。
- 想提交、handoff、发布或进入下一步，但没有新鲜验证证据。
- 用局部测试、旧日志、agent 自报成功或视觉观感替代当前范围验收。
- 为了结束任务而忽略未验证区域、open questions 或 failed checks。
- 连续修复后出现新的共享状态、架构、范围或定义漂移问题。

## Rationalization Check

| 借口 | 现实 |
| --- | --- |
| “改动很小” | 小改只降低验证成本，不取消验证。 |
| “validator 通过了” | validator 只证明契约，不证明真实业务效果。 |
| “之前跑过” | 旧证据不能证明当前 diff。 |
| “没有时间完整验证” | 可以降级为 `PARTIAL`，不能声称 `PASS`。 |
| “用户没有明确要求测试” | 只要声明完成，就需要相称证据。 |

## 人工介入

如果同一问题连续 3 次修复仍失败，或每次修复都暴露新的架构、范围、权限、数据或业务定义问题，停止继续尝试，向用户说明证据、失败模式和可选路径，再请求人工决策。
