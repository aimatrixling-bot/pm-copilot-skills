# UI/UX 设计原则

AI Builder OS 的 UI/UX 契约服务于可构建、可评审、可验证的产品产物，不服务于装饰性展示。

## 基本原则

- 业务清晰优先于视觉炫技。
- 先确认用户、场景、任务和信息层级，再定义页面。
- 先复用现有组件和样式，再考虑新增模式。
- 状态完整性是设计质量的一部分，不是实现细节。
- 原型、spec、agent task、review 必须使用同一份 Design Brief 或明确说明偏离原因。
- Mock/demo 数据必须标注，不得伪装为真实生产数据。
- 界面本体只放用户真实可见、可理解、可操作的内容；非界面业务规则说明必须进入独立区域。

## 信息层级

每个 UI 产物必须说明：

- 主用户是谁。
- 当前页面或流程帮助用户完成什么任务。
- 页面第一视口最重要的信息是什么。
- 次要信息如何组织。
- 哪些操作是主操作、次操作、危险操作。
- 哪些内容可以延后、折叠或移到详情页。

## 设计输入

进入 UI/UX 输出前，应尽量具备：

- Feature Frame 或 Builder Spec。
- 目标用户和核心场景。
- 主要任务流。
- 需要覆盖的状态。
- 现有产品、设计系统或组件约定。
- 验收和验证方式。

## 设计输出

UI/UX 输出至少应说明：

- 信息架构。
- 核心流程。
- 组件选择。
- 状态覆盖。
- 交互反馈。
- 响应式要求。
- 可访问性基础。
- 与既有视觉约定的关系。
- 未覆盖或暂时 mock 的部分。
- `ui_content_boundary`、`business_rule_notes`、`rule_notes_placement` 和 `non_ui_explanations`，用于防止业务逻辑说明侵入界面主体。

## 产品逻辑说明边界

业务规则补充说明是必要的，但默认不是界面内容。计算规则、权限矩阵、状态机、字段映射、接口说明、mock/demo 限制和评审备注，应放在界面预览下方的 `业务规则说明（非界面内容）` 区域，或链接到 spec / Design Brief / 业务规则文档。

只有当这些说明是用户真实需要阅读的产品功能，例如帮助抽屉、规则提示、详情页说明或审批原因展示时，才可以放入界面本体，并且必须在 Design Brief 中标注为用户可见内容。
